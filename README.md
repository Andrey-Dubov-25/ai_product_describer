# AI-помощник для товарных описаний

Прототип сервиса на **FastAPI + Groq**, который по входным данным о
контрольно-измерительном приборе генерирует черновик карточки товара для
B2B-интернет-магазина: SEO-заголовок, SEO-описание, ключевые характеристики,
поисковые запросы и commercial-блок для менеджера.

## Что делает сервис

1. Принимает данные о товаре в JSON (или через веб-форму на `/`).
2. Отправляет их в LLM (Groq, модель `openai/gpt-oss-120b`) с продуманным промптом.
3. Возвращает структурированный результат, готовый для копирования контент-менеджером.
4. Явно сообщает, каких полей не хватило для полной карточки.

**Ключевой принцип:** модель пишет только текст (SEO, запросы, commercial-блок).
Технические характеристики (`key_specs`) и список пропусков (`missing_fields`)
собираются в коде из входных данных — выдумать характеристику физически невозможно.

## Установка

1. Клонируйте репозиторий:
   ```bash
   git clone https://github.com/Andrey-Dubov-25/ai_product_describer.git
   cd ai-product-describer
   ```

2. Создайте виртуальное окружение и активируйте его:
   ```bash
   python -m venv .venv
   source .venv/bin/activate        # Linux/macOS
   # .venv\Scripts\activate         # Windows
   ```

3. Установите зависимости:
   ```bash
   pip install -r requirements.txt
   ```

4. Получите бесплатный API-ключ Groq: https://console.groq.com/keys

5. Скопируйте `.env.example` в `.env` и вставьте ключ:
   ```bash
   cp .env.example .env
   ```
   ```env
   GROQ_API_KEY=ваш_ключ
   # GROQ_MODEL=openai/gpt-oss-120b   # опционально, модель по умолчанию
   ```

## Запуск

```bash
uvicorn app.main:app --reload
```

- **Веб-форма:** http://127.0.0.1:8000/ — заполнить поля и нажать «Сгенерировать».
- **Swagger:** http://127.0.0.1:8000/docs — интерактивная документация API.

## API

### `POST /api/generate`

Принимает данные о товаре, возвращает черновик карточки.

**Запрос:**
```json
{
  "name": "Манометр показывающий DM Ø2",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

**Ответ:**
```json
{
  "seo_title": "Манометр DM Ø2 от Манотомь, диапазон 0–1,6 МПа, точность 1,5",
  "seo_description": "Манометр показывающий DM Ø2 от производителя Манотомь...",
  "key_specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм",
    "питание": "данных нет",
    "интерфейсы": "данных нет",
    "тип корпуса": "данных нет"
  },
  "search_queries": [
    "манометр DM Ø2 0-1,6 МПа",
    "манометр Манотомь класс точности 1,5",
    "манометр с присоединением G1/2"
  ],
  "commercial_block": "Прибор подойдёт тем, кто измеряет избыточное давление...",
  "missing_fields": ["питание", "интерфейсы", "тип корпуса"]
}
```

**Коды ответов:**

| Код | Когда |
|---|---|
| 200 | Успех |
| 422 | Пустой `specs` или невалидный JSON |
| 500 | Внутренняя ошибка |

## Принятые решения

**Модель `openai/gpt-oss-120b` через Groq.** Бесплатный tier, быстрый inference,
поддержка `response_format={"type": "json_object"}`.

**Характеристики не проходят через модель.** `key_specs` собирается в коде из
входных `specs`, отсутствующие поля заполняются `"данных нет"`.

**`missing_fields` тоже считается в коде** — список полей из `EXPECTED_SPEC_KEYS`,
которых нет во входе.

**Промпт с явным списком запретов.** Модели запрещено упоминать материал корпуса,
отрасли применения, калибровку, интеграцию с системами — если этого нет во входе.

**Веб-форма.** Один HTML-файл без сборки и зависимостей — чтобы
контент-менеджер мог проверить сервис без curl и Swagger.

**API-ключ только в `.env`.** Файл в `.gitignore`, в коде ключа нет.

## Ограничения

- **Описательные домыслы в тексте.** Модель может добавлять обороты, типичные для
  КИП («корпус устойчив к коррозии», «подходит для пищевой отрасли»), даже если
  их нет во входных данных. Технические характеристики при этом всегда точны.
  Для продакшена потребовалась бы пост-проверка текста (словарь запрещённых
  терминов, NER) или ручная вычитка контент-менеджером.
- **`seo_title` может превышать 70 символов.** В промпте указано «до 70 символов», 
  модель обычно следует, но не гарантированно.
- **`seo_description` может быть короче 800 символов** при бедном входе. Это
  осознанный компромисс: лучше короче, но без выдуманных фактов.
- **Нет пакетной обработки.** Один товар — один запрос. Для массовой генерации
  карточек потребовался бы batch-эндпоинт и очередь.
- **Нет кэширования.** Повторный запрос с теми же данными снова идёт в LLM.

## Что можно улучшить

- Post-фильтр текста на запрещённые термины (снизит описательные домыслы).
- Batch-эндпоинт для обработки списка товаров.
- Кэш ответов по хэшу входных данных (Redis или файловый).
- Юнит-тесты на сборку `key_specs` и `missing_fields`.
- Экспорт в Markdown/CSV для контент-менеджера.
